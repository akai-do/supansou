## 0. 结论摘要（一页）

### 0.1 一句话判断

aliso.vip 的强项是**搜索过程可视化、结果聚合与交付转化**；本站的强项是**链接可直接使用、有效性可验证、索引可积累、下载可加速**。统一路线不是“做成 aliso”，而是**补齐搜索体验层，同时守住差异化护城河**。

### 0.2 aliso 值得学的五件事

1. **搜索过程可见**：搜索中显示当前结果数、网盘类型数、用时，并允许停止（`/search?ai=庆余年` 实测 581 条 / 10 类 / 8.1s；脚本 `Home-Bv-pxTTG.js` 确认 `AbortController`）。
2. **筛选带计数**：每个网盘 chip 显示当前结果集的数量，用户能判断“哪个网盘有货”。
3. **同名变体可切换**：同一资源的多个链接用编号切换，不产生新路由（脚本与页面均确认）。
4. **交付层统一**：扫码、保存网盘、复制分享集中在一个弹窗；百度资源显示提取码（页面与脚本确认）。
5. **发现入口前置**：首页用热门/历史/本地三行词条把用户直接送进搜索（`/` 页面与初始化请求确认）。

### 0.3 本站不能丢的七项优势

直链可用与复制提取码；有效性三态 + 巡检 + 举报；本地索引/收割/零结果守望；百度下载加速（aria2/账号池/本机 Hook）；豆瓣榜单与海报；统计页；分页/缓存/来源/时间等工程细节。

（来源：`docs/04` §7；`06-gap-analysis.md` §3 逐项确认；代码见 `backend/` 与 `frontend/src/`。）

### 0.4 统一后的第一批动作（P0）

| 顺序 | 动作 | 为什么先做 |
|---|---|---|
| 1 | 搜索状态条：耗时、结果数、类型数、进行中/完成/失败 | 成本低、感知强，直接补最大体验差 |
| 2 | 网盘计数 | 让筛选从“有分类”变成“可决策” |
| 3 | 网盘多选 + URL 状态 | 后端已支持 `disk_types` 数组，前端只需升级 |
| 4 | 排序（默认/时间/名称） | 后端分页要求服务端排序；成本可控 |
| 5 | 同名变体编号 chip | 纯前端改造，减少纵向滚动 |
| 6 | 移动端修复：tabbar 图标、搜索框同步、筛选横滑 | 已有明确代码缺陷，修复即可 |
| 7 | 二维码补充交付 | 纯前端、可回滚；不改变直链主路径 |
| 8 | 公告条 + 法律页 | 合规必需；法律页当前**不存在**，需从零建 |

### 0.5 三个必须记住的事实修正

1. **网盘类型数量不是“14 对 10”的对错题**：配置决定类型全集（公开配置返回 15 条记录），筛选器展示启用的类型（04 当次看到 14 个），结果页只展示当前结果中出现的类型（新版实测 10 类）。三个数字口径不同。
2. **首页“历史”范围未确认**：aliso 既有 `localStorage.alipansou_search_history`，也有 `GET /api/search-history`；不能断言是全站还是本机，统一标“待确认：本机/全站/混合”。
3. **“5 分钟后删除”是旧版人工观察**：新版只确认弹窗结构，没有确认该文案与计时，不能当事实引用。

### 0.6 还有哪些未解决

见 §11。最重要的四项：aliso 历史范围、失效隐藏图标、5 分钟文案、流式分帧格式。这些都不阻塞 P0。

## 2. 信息架构

### 2.1 aliso 的公开站点结构

```text
https://aliso.vip/
├── /                         首页
│   ├── 顶部工具栏：视频解析（外站）/ 提交需求 / 分享获益（外站）/ 少儿资源库（外站）/ 主题
│   ├── 主搜索区：Logo + 站点名 + 公告 + 搜索框
│   ├── 快捷发现：热门 / 历史 / 本地（三行横向词条）
│   ├── 运营位：小程序 banner、搜索页内嵌广告/底部广告
│   └── 页脚：友链、©、净网/版权/免责声明
├── /search?ai=<关键词>       搜索结果
│   ├── 顶部搜索框（回填关键词）
│   ├── 状态条：当前显示 / 网盘类型 / 用时 / 持续搜索中或已取消
│   ├── 排序：默认 / 时间 / 名称
│   ├── 网盘筛选 chips（带数量，单选）
│   ├── 结果卡片 + 同名更多结果编号 + 广告
│   ├── 资源获取弹窗（二维码 / 提取码 / 保存 / 复制）
│   └── 页脚
├── /demand                   资源需求
│   ├── 提交需求（资源名/平台/地址/备注/联系方式/付费意愿）
│   └── 历史需求（排名/状态/日期/想要数/投票）
└── /admin/*                  管理后台（仅静态发现，未访问）
    dashboard / resources / clouddrive / source-center / api-config /
    alipansou-manage / search-ranking / settings / demands
```

来源：`01-information-architecture.md` §1；公开 bundle 路由表；页面观察；04 的移动端/运营位/法律页观察。

### 2.2 页面关系

1. 首页和搜索结果**复用同一个 `Home` 组件**，根据 `route.path` 与 `route.query.ai` 切换视图（`04-frontend-profile.md` §3）。
2. 搜索结果**没有独立详情路由**；资源详情是弹窗，URL 停留在 `/search?ai=`，刷新不恢复弹窗。
3. “同名更多结果”是同一资源的多个链接变体，用编号切换，不产生新页面。
4. 需求页是公开页面；历史需求无需登录即可查看，“想要”是公开投票行为。
5. 管理后台是独立路由树，需登录；本次仅从公开 bundle 发现路由与接口名，未访问、未验证。

### 2.3 本站当前的信息架构

```text
/                -> 重定向到 /resource
/resource?kw=    -> 资源搜索（SearchDock + ResourcePage）
/douban          -> 豆瓣榜单
/accel           -> 网盘加速
/guest           -> 直链解析
/booster         -> 下载提速
/stats           -> 数据统计
/:pathMatch(.*)  -> 重定向到 /resource
```

来源：`frontend/src/router.js:11-19`。

本站**没有独立首页**：搜索、热搜、历史、筛选都在 `/resource` 内；PC 左侧栏 6 项，移动端底部 tabbar 6 项（`AppShell.vue:19-26`）。这带来两个直接结论：

- 不需要为了“像 aliso”而强行增加首页；可以把“快捷发现”前置到 `/resource` 未搜索态（现在已经显示热搜 + 本机历史）。
- 如果要做“本地归档”入口，放在侧栏/移动菜单/未搜索态都合理；不需要新建首页。

### 2.4 架构启示

- 首页承担“搜索 + 发现 + 运营”三合一；本站可用 `/resource` 未搜索态承担“搜索 + 发现”，运营位按需增加。
- 搜索页的状态条、筛选计数、排序、同名变体是体验差异最大的部分，均可在现有页面上增量实现。
- 资源弹窗是“交付层”，不是“详情页”；本站已有直链/复制能力，二维码应作为补充。
- 需求板是独立社区功能，取决于运营投入；不应为了对标而引入无人维护的表单。
- 管理后台不需要整体复刻；本站已有站长令牌、加速管理、统计能力，优先做轻量站点配置。

## 4. 核心交互流程

### 4.1 首页加载

```text
打开 /
  -> SPA 外壳（title/meta/OG/统计脚本）
  -> 加载 Vite 入口
  -> 懒加载 Home chunk
  -> 并行请求：settings / netdisk-configs / enabled-check-services /
              hot-search-words / search-history / resource-titles / notice
  -> 渲染：Logo、公告、搜索框、热门/历史/本地三行、运营位、页脚
```

证据：`03-interaction-flows.md` §1.1；`Home-Bv-pxTTG.js`；公开 GET。  
本站对应：`/` 直接重定向 `/resource`，无首页加载链路；未搜索态显示热搜 + 本机历史（`ResourcePage.vue:420-444`）。

### 4.2 搜索状态机（最重要的借鉴）

aliso 的状态可以抽象为：

```text
idle
  -> searching（计时开始，结果 0）
  -> streaming（每批结果追加：更新列表/总数/类型数/各网盘计数）
  -> done（停止计时，显示最终数量/类型/用时）
  -> cancelled（用户 abort，保留已收结果，显示“已取消”）
  -> failed（流式失败/无结果 -> 回退 /api/search -> done）
  -> empty（结束且 0 结果 -> 空态 + 登记需求）
```

关键事实：

- 搜索请求：`POST /api/stream-search`，body `{kw, src:"all"}`，头可带 `X-Search-Token`；按行读取响应。
- 取消：`AbortController.abort()`；已收到的结果保留。
- 回退：流式失败/无结果时 `POST /api/search`。
- 实测：`/search?ai=庆余年` 当前显示 581、网盘类型 10、用时 8.1s、状态“持续搜索中”；10 类计数之和为 581。
- 未验证：搜索按钮/回车的具体绑定（自动化未稳定触发）；分帧格式；服务端结束标记。

本站目标状态机（P0 先做简化版）：

```text
idle
  -> loading（前端计时开始；显示骨架屏 + 已用时）
  -> done（显示结果数/类型数/耗时/实时/历史/检测/缓存）
  -> empty（空态）
  -> error（显示错误；不显示错误耗时）
```

P1 再升级为 `streaming/cancelled`。

### 4.3 筛选与排序

aliso：

- 默认“全部”；点击网盘 chip 单选高亮；计数来自当前结果集。
- 排序下拉：默认保持原始顺序；时间降序；名称排序。
- 排序是前端计算属性；筛选/排序状态未观察到写入 URL（`04-frontend-profile.md` §4.3）。

本站：

- 服务端筛选：`searchParams()` 只传单个 `disk_types`（`ResourcePage.vue:155-159`）；后端支持数组。
- 服务端分页：排序必须在后端完成，否则只排当前页会误导用户。
- 目标：多选 + URL 状态（`?disk=quark,baidu&sort=time`），刷新/前进后退可恢复。

### 4.4 资源交付

aliso：

```text
点击卡片/获取资源
  -> 上报网盘点击
  -> 打开弹窗（加载态）
  -> 百度：读取配置中的提取码
  -> 若启用转存：请求转存，成功后替换链接/提取码
  -> 生成二维码
  -> 展示：二维码 + 提取码 + 标题（可展开）+ 保存网盘 + 复制分享
```

证据：`03-interaction-flows.md` §3；`05-public-api-observations.md` §3。  
未验证：转存真实响应、二维码在各网盘 App 的可识别性、提取码展示条件。

本站目标：

```text
卡片/抽屉
  -> 直链打开（主路径）
  -> 复制链接 / 复制提取码（主路径）
  -> 二维码（补充路径，只编码分享链接）
  -> 失效举报（保留）
  -> 变体切换（编号 chip）
```

原则：**不把扫码变成唯一交付方式**；二维码只服务“手机打开”场景。

### 4.5 需求提交

aliso：

```text
/demand -> 默认提交 Tab
  -> 校验资源名/平台
  -> POST /api/demand
  -> 成功：提示、清空、刷新历史
  -> 历史 Tab：GET /api/demands + /api/demands/wanted
  -> 想要：POST /api/demand/{id}/want
```

证据：`03-interaction-flows.md` §4；`05-public-api-observations.md` §4。本次未提交真实需求。  
本站：无需求板；如做，先匿名 + 站长审核 + 想要投票 + 防刷（P2，触发式）。

### 4.6 失败与降级

| 场景 | aliso 表现（来源） | 本站现状/目标 |
|---|---|---|
| 流式失败 | 回退 `/api/search`（`Home.js`） | 本站无流式；一次性请求失败显示错误，可重试 |
| 搜索取消 | 保留已收结果，显示“已取消”（`Home.js`） | P1 随流式实现 |
| 搜索无结果 | 空态 + 登记需求（`Home.js`） | 已有空态；可补反馈入口 |
| 屏蔽词 | 前端提示包含屏蔽词（`Home.js`） | 未验证本站是否有对应策略 |
| 需求校验失败 | 资源名/平台提示（`Demand.js`） | 如做需求板必须 |
| 网络异常 | “网络错误，请稍后重试”（`Demand.js`） | 本站搜索显示请求失败信息（`ResourcePage.vue:149-151`） |
| 转存/二维码失败 | 脚本有 try/catch；UI 未验证 | 做二维码时必须有失败占位 |

### 4.7 本站流程改造的边界

- 不重写搜索管线；先加状态、计数、排序、变体。
- 不把分页改成无限列表；aliso 的一次性渲染不适合大结果集。
- 不引入扫码-only；直链/复制仍是主路径。
- 不为了“过程感”牺牲稳定性；耗时/状态可以在一次性请求上先实现。

## 8. 不建议照搬的点

1. **扫码-only 交付**：会伤害桌面用户体验和链接可复制性；本站保留直链，二维码只作补充。
2. **一次性渲染全部结果**：结果多时性能/可访问性差；本站分页是优势。
3. **公开他人原始搜索历史**：aliso 首页“历史”的范围尚未确认；本站坚持本机历史 + 聚合热搜，不展示他人原始搜索词。
4. **过度运营位**：小程序、邀请注册、站长二维码、搜索中广告会稀释搜索体验；按自己的运营能力取舍。
5. **复刻视觉/文案/代码**：只借鉴交互模式，独立实现；不复制页面结构、样式、图片、字体、文案。
6. **抓取/调用对方接口**：不把 aliso 作为数据源；数据来自自己的 PanSou/插件/索引。
7. **整体复刻管理后台**：对方后台覆盖资源/网盘账号/源库/接口配置/排名/需求审核；本站优先复用现有站长/加速/统计能力，做轻量站点配置即可。
8. **默认开启转存/保存网盘**：需要账号、授权、合规评估；不要把 Cookie/令牌暴露到前端；与现有加速账号体系隔离。
9. **无运营计划就上需求板**：匿名表单会迅速变成垃圾板；没有审核/防刷/响应能力就不要做。
10. **第三方统计脚本**：百度统计/MXA 不照搬；如需统计，优先自建或选择合规方案。
11. **把旧版未复验观察当事实**：眼睛图标、“5 分钟后删除”、全站历史，都必须标注“旧版观察/未复验”。

## 9. 统一改进路线（P0/P1/P2）

### 9.1 优先级定义

这里的 P0/P1/P2 是**交付批次**，不是功能价值标签：

- **P0**：第一个迭代（约 1~2 周），直接影响搜索主流程，成本低~中，风险可控，可独立回滚。
- **P1**：第二个迭代（约 2~3 周），需要后端/数据/协议配合，或需要新的页面/组件。
- **P2**：可选/运营型/触发式；没有明确收益或运营投入时不做。

这解释了为什么“渐进式搜索”在 02 里标 P0、在 07 里放 P1：它的**功能价值是 P0**，但**工程成本和上游兼容风险**使它不适合作为第一个迭代。统一版把它放 P1。

### 9.2 P0：第一个迭代

| ID | 改进项 | 用户价值 | 成本 | 风险 | 来源 | 说明 |

**计数口径说明**：`disk_counts` 应优先基于**未筛选的完整结果集**计算；如果 P0 为了降低改动继续把 `disk_types` 透传给上游，则必须在筛选态隐藏计数（只显示当前结果数），避免出现“计数 283、列表 0”的矛盾。具体取舍见 `10-unified-implementation-plan.md` U-P0-2 的方案 A/B。

**P0 排序理由**：

- 1~4 是搜索主流程的“信息与决策”层，成本可控，收益立竿见影。
- 5、7 是低风险前端改造，适合并行。
- 6 是已确认的代码缺陷，必须修。
- 8 合规价值高，但法律文案需要审核；可与 1~7 并行，不阻塞搜索体验上线。

**P0 验收总则**：

- 搜索完成后 1 秒内显示耗时、结果数、类型数。
- 计数与结果一致；多选后结果/计数/URL 正确联动。
- 排序切换后 URL 可分享，刷新保持；默认排序与改动前一致。
- 变体切换无需刷新；当前变体高亮；失效变体有标识。
- 390px 无横向溢出；tabbar 图标可见；搜索框路由同步；筛选可横滑。
- 二维码可被手机相机/网盘 App 识别；直链/复制不回归；二维码不含 Cookie/账号/令牌。
- 公告可配置/可关闭/刷新不重复打扰；法律页可访问；移动端公告不横向裁切。
