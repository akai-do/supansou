# PanSou 上游、aliso.vip 与 DuPanSou-Archive 差距分析

- 分析日期：2026-10-19
- 对比对象：
  - PanSou 上游：`fish2018/pansou`（MIT）
  - aliso.vip：公开页面/公开 bundle/公开只读接口观察
  - 本站：`DuPanSou-Archive` 当前代码（Flask + SQLite + Vue 3 + PanSou 运行时依赖）
- 参考：`docs/04-aliso公开页面对标与改进规划.md`、本目录 `01`~`05` 文档

## 1. 结论先行

1. **aliso.vip 不是“另一个 PanSou 前端”那么简单**。它在 PanSou 之外做了：流式搜索、网盘计数/排序、同名变体、资源弹窗/二维码、需求板、站点配置、管理后台、统计与运营位。
2. **本站的核心优势不在“像 aliso”**，而在：直链可用、有效性三态检测、本地索引/收割、百度下载加速、豆瓣榜单、统计页。对标时不能为了追交互而丢掉这些优势。
3. **最值得补的差距是搜索体验层**：耗时/进行中/可取消、网盘计数与多选、排序、同名变体、二维码补充交付、移动端细节。
4. **需求板是运营型功能**，收益取决于持续运营；建议先做匿名提交 + 站长审核 + 想要投票 + 防刷，或者暂缓。
5. **管理后台不需要整体复刻**。本站已有站长令牌、加速管理、统计等能力，优先把“公告/首页词条/网盘配置”做成轻量配置即可。

## 2. PanSou 上游能力基线

PanSou 上游（MIT）提供的核心能力：

- 搜索聚合：Telegram 频道 + 插件来源并发搜索。
- 排序：插件等级、更新时间新鲜度、优先关键词。
- 网盘分类：baidu、aliyun、quark、guangya、tianyi、uc、mobile、115、pikpak、xunlei、123、magnet、ed2k、others。
- 插件系统：异步插件、“尽快响应、持续处理”。
- 缓存：内存分片 + 磁盘分片。
- API：
  - `POST /api/auth/login`
  - `POST /api/auth/verify`
  - `POST /api/auth/logout`
  - `POST/GET /api/search`
  - `POST /api/check/links`
  - `GET /api/health`
- 搜索参数：`kw`、`channels`、`conc`、`refresh`、`res`（all/results/merge）、`src`（all/tg/plugin）、`plugins`、`cloud_types`、`ext`、`filter`（include/exclude）。
- 前端集成版：`ghcr.io/fish2018/pansou-web`；纯后端版：`ghcr.io/fish2018/pansou:latest`。
- 许可证：MIT；作者声明“仅供学习研究，请勿以各种形式用于盈利目的”（以 LICENSE 与仓库声明为准）。

### 2.1 上游没有直接提供的东西

- 没有“阿立盘搜”式的公开站点 UI（首页跑马灯、需求板、资源弹窗）。
- 没有公开的流式搜索接口（上游是请求/响应式；aliso 的 `/api/stream-search` 是其自建层）。
- 没有公开的需求板、管理后台、站点配置、广告位。
- 没有“同名变体编号”“网盘计数”“二维码交付”等前端交互。

结论：aliso 的差异化主要在 **自建后端聚合层 + Vue 前端 + 运营后台**，不是 PanSou 上游本身。

## 4. 本站与 aliso 的主要差距

### 4.1 搜索体验层（P0）

1. **过程感**：aliso 有“当前显示/网盘类型/用时/持续搜索中/取消”；本站是一次性请求 + 骨架屏。
2. **网盘计数**：aliso 每个 chip 带数量；本站没有 `disk_counts`。
3. **排序**：aliso 有默认/时间/名称；本站搜索页无排序入口。
4. **同名变体**：aliso 用编号快速切换；本站是展开行。
5. **交付层**：aliso 用弹窗 + 二维码 + 保存/复制；本站是卡片内直链 + 复制，缺少二维码和统一弹窗。
6. **移动端**：aliso 有横向筛选、汉堡菜单；本站 tabbar 图标缺失、筛选换行。

### 4.2 数据与索引层（P1）

- 本站已有本地索引、收割、零结果守望、拼写纠错，但前端没有“本地归档”入口。
- aliso 的“📁本地”行说明它把本地资源标题用于首页发现；本站可以把 `/api/archive` 和本地索引变成可见功能。
- 本站的 SQLite `LIKE` 查询在数据量大后可能成为瓶颈；可评估 FTS5。

### 4.3 运营与合规层（P1/P2）

- 本站缺少公告条、法律页入口、首页运营位。
- aliso 有需求板、小程序、邀请注册、友链；本站应按自身运营能力取舍。
- 本站已有 `ACCEL_TOKEN` 硬编码风险（见仓库改动分析），与对标无关但应在公开部署前处理。

### 4.4 管理后台（P2/不做整体复刻）

aliso 后台覆盖：控制台、资源、网盘账号、源库、接口配置、盘搜管理、搜索排名、设置、需求审核。

本站现状：
- 有站长令牌、加速管理、解析口令、任务管理、统计。
- 没有通用资源管理/网盘账号/源库/需求审核后台。

建议：
- 先做 **站点配置**（公告、首页词条、广告位、网盘类型开关）的轻量配置。
- 不做大规模后台复刻；按实际运营需要增量建设。

### P0（1 周内可落地，直接提升搜索体验）

## 7. 风险与约束

1. **流式搜索与 PanSou 上游兼容性**：上游是请求/响应式；要做渐进式搜索，需要在本站后端做多源并行/分块，而不是假设上游支持 SSE。
2. **`disk_counts` 的性能**：大结果集上要做一次聚合；建议在后端分页/分组时顺手计算，避免前端二次遍历。
3. **排序语义**：默认排序应保持本站已有的相关度/存活/点击热度；时间/名称排序只改变展示顺序，不应破坏有效性降权。
4. **二维码安全**：二维码只编码分享链接；不要把提取码、Cookie、账号信息写进二维码。
5. **需求板防刷**：匿名提交需要 IP/频率限制、内容审核、敏感词过滤；否则会迅速变成垃圾板。
6. **合规**：功能思路可以借鉴，代码/样式/文案/图片不能复制；数据源必须自己的。
7. **现有密钥风险**：仓库改动中 `ACCEL_TOKEN` 在 `docker-compose.yml`、bat、vbs 中硬编码；公开部署前应改为环境变量/本地配置。

## 8. 建议的落地顺序

```text
第 1 周：P0-1 ~ P0-7（状态条、计数/多选、排序、变体、二维码、移动端、公告/法律）
第 2 周：P1-8 ~ P1-10（渐进搜索、本地归档、详情抽屉）
第 3-4 周：P1-11 ~ P1-12（批量检测上屏、站点配置）
之后：根据运营数据决定 P2（需求板、多站点、转存、小程序）
```

衡量指标：

- 搜索到点击/复制/打开的转化率；
- 筛选/排序使用率；
- 零结果率、平均搜索耗时、首条结果出现时间；
- 失效举报率、有效链接占比；
- 移动端跳出率、tabbar 使用率；
- 如做需求板：提交量、解决率、平均想要数、垃圾需求比例。
