## 4.1 执行方案（口径：越快越好，不设硬数字；范围：只做定论 + 最少仪器修复）

一句话目标：给"真实下载下是否还衰减"定论，同时产出**"最高不衰减倍率"这个具体数字**，写进 V4 交接。本轮不改 native、不动前端、不碰 4.2 自动化缺口。

---

### 阶段 0 · 最小仪器修复（只改 `scripts/_diag_client_booster.py`）

前两条是必须的，因为不修的话跑出来的数字无法支撑定论；后四条都在同一个采样主循环里，几行改动，不新增依赖：

- **R1（必须）修首窗口计算** `:329-338`。现在 `window_bytes(0, win)` 因 `a == 0` 特例返回 `cum[win-1] - 0`，也就是**引擎进程自启动以来的全部读字节**，不是首窗口增量；偏大还是偏小取决于进程刚起还是跑了很久，于是**段间不可比**——而段间可比正是对照实验唯一需要的东西。修法：采样循环前先读一帧 t0 基线进 `cum`，之后 `window_bytes(a,b) = cum[b] - cum[a]`，删掉特例。V3 里 `engineF5 末/首 33%`（工具口径就是"衰减"）与叙述"没有观察到衰减"自相矛盾，很可能就是这个 bug 造出来的假象。
- **R2（必须）hook 在位真值改走模块枚举**。`eject` 之后 `status` 会重新打开同名映射打印旧值（4.3-3），实测 `client_ab.csv` 第一行就是 `baseline` 段却带着 `qpcFactor=5.001 / refreshCount=7`——因为基线段 `hooks_expected=False`、不校验不变量、`inv_ok` 无条件写 1，旧值照样入表，任何人回看都会判定这条基线被污染。修法：复用 `_diag_client_procs.py:22` 的 `mods(pid)`（`Module32FirstW`，跨 WOW64 可用），新增 CSV 列 `hook_present / speedpatch_present / engine_pid`，`status` 降为辅助信息。
- **R3（必须）不变量新增"`hook32.dll` 必须在位"**；基线段不再无条件 `inv_ok=1`，改成"无 hook 预期且确实不在位"才算通过。
- **R4（必备）窗口长度固定为 60s**，不再用 `win = max(3, n//5)`，让不同时长的段算同一个物理窗口。
- **R5（必备）段内引擎 pid 变化即作废该段并打印原因**。客户端会自己重启 `baidunetdiskhost.exe`，pid 一变旧 pid 的累计值走平，会输出一个假的"衰减"。
- **R6（便宜）复用手上样本算停摆占比 / 最长停摆 / 停摆间隔随时间的走势**。这是 OpenSpeedy 式塌陷最早的信号（间隔逐渐拉长），且能区分"服务端限速"与"hook 副作用"——后者是本轮要判的。

### 阶段 2 · 选一个撑得住的观测对象（本轮第一道闸门）

按上述账，现有对象只剩约 1.7GB / 约 14 分钟，不够。优先级：

- **(a) 零成本**：`python scripts/_diag_client_tasks.py list`，若队列里已有 ≥8GB 剩余的大任务（表里最多看 60 行），直接用它当对象。
- **(b) 你点一下**：若队列里都偏小，你在客户端里手动把一个大文件（≥8GB，或几个 3GB+ 依次）加入下载并开始。UI 自动化已确认走不通（4.3-4），这一步只能人工。这是最省事的路径。
- **(c) 兜底（有代价，我会先把要删的路径列给你确认）**：改用"**同一文件 + 重置进度**"设计——删掉该任务的 `.downloading` 分片 + 复位 `download_file.status`，让 3.2GB 文件从头再下一遍。代价是重下约 3×2.4GB 流量（文件本身最终仍会下完，只是白跑流量）；收益明显：**每个 pass 都从同一批分片、同一顺序、同一初始状态开始**，比"同一段下载的两个时间窗"干净得多——目前 V3 把"F=1 对照段"判为污染，根因就是这个窗口不等价。

对象确定后立刻跑 `python scripts/_diag_client_booster.py check` 拿到**下载引擎 pid**（不是 `BaiduNetdisk.exe`），后续 inject/setspeed/status/eject 全用这个 pid。

### 阶段 3 · 阶梯对照（`--probe off` 全程，避免自测的 1s 等待给客户端加负载）

| 段 | 状态 | 时长 | 作用 |
|---|---|---|---|
| S0 | 无 hook（先全量 `eject` + 模块校验不在位） | 300s | 干净起点 |
| S1 | 无 hook | 600s | **V3 缺失的真基线**：客户端自己在长窗里掉不掉 |
| S2 | 注入 F=1 | 300s | 把"DLL 本身的开销"与"加速效果"分开 |
| S3 | F=5 | 600s | 核心问题 |
| S4 | F=8 | 600s | 追上限（你的口径：越快越好） |
| S5 | F=10 | 600s | 追上限 |
| S6 | 回 F=5 | 300s | 漂移校验 + 可逆性：若 S6 明显低于 S3，说明是时间漂移而非倍率 |

约 60 分钟观测。若对象只够约 30 分钟，砍 S5 与 S2，保 S1/S3/S4/S6/S7。**全程禁止 `native/build.bat`**：DLL 被占会 LNK1104，且会重启 host 进程打断下载。

### 阶段 4 · 定论

先过信任门槛（不变量通过率 ≥90% 且 hook 在位状态与声明一致 且 引擎 pid 未变 且 停摆占比 <15%），再看末 60s / 首 60s 窗口比例。判定表：

| 现象 | 结论 |
|---|---|
| S1 无 hook 也衰减 | 衰减是客户端/服务端特性，与 hook 无关 → 赌注前提被改写 |
| S1 稳住、S3–S5 衰减 | **选择性 hook 没能解决 OpenSpeedy 的老问题**（赌注失败） |
| S1 稳住、S3–S5 也稳住 | **赌注成立**，M1-b-3 定"稳住" |
| 平台 ÷ S1 平台 ≈ 倍率 | 时钟倍率线性生效 |
| F=8/F=10 平台不涨（卡 ±4MB/s 附近） | 瓶颈在服务端单分片下发速率 → 记录转向点 |

产出：`项目计划/BOOSTER_HANDOFF_V4.md`（含定论、最高不衰减倍率、可信段与被排除段的理由）+ 原始数据落 `backend/data/clean_ab/`，同步更新 M1-b-3 / M2 状态。

### 最终成果（越快越好口径）

- **赌注成立**：拿到"最高不衰减倍率"这个具体数字（预期 5–8×），它直接就是 M2 闭环里 `COLLAPSE_RATIO / WIN_SEC / FLOOR_BPS` 的标定输入，也是侧边栏"打开客户端点下载自动完成"的默认档。量级参照：注入态段均值约 2MB/s，未注入约 0.55MB/s（3.5–4.5×）。
- **卡在单分片上限**：结论变成"hook 的时钟倍率天花板 = 服务端单分片下发速率"。价值是用一次 60 分钟对照**把这条路走死**，资源立刻转到已完成的那条直链线 + 多分片并发，绕开客户端"一次只吃一个块"的串行约束。

- 下载由你保证（UI 自动化不可用）；中途任务停了，该段按停摆占比自动作废，不硬凑结论。
- 阶段 2(c) 删分片/改任务库前有 `backend/data/task_db_backup/` 整库备份 + `restore` 一键回滚，且只动 `download_file.status`。
